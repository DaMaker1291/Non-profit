## A. Product overview — what OpenMind is today

OpenMind is a **self-hostable, single-laptop, offline-capable learning application** for secondary-school
students (roughly ages 11–18) covering **five subjects** through **135 atomic concepts**. It is a
Next.js 15 application with a file-backed data store, 47 API route handlers and 26 pages. It runs with
**no database and no API key**, and its own documentation describes it as "education infrastructure,
not another AI tutor": the AI is optional and every AI-dependent surface has a deterministic fallback.

**What genuinely works today, on this tree:**

- A visitor can arrive, complete a six-step enrolment (country → year → pathway for two-system
  countries → subject → qualification → tier → board → exam date → daily minutes → language), sit an
  adaptive diagnostic, be taught, practise, prove, transfer, sit an exam-style paper, see their
  evidence, and delete or export everything. **Verified end to end over HTTP (860 assertions, 0
  failed) and in a real Chromium browser (65 + 25 assertions, 0 failed).**
- A teacher can create a class, share a join code, and see per-concept mastery and class-wide
  misconception aggregation derived from members' evidence ledgers — **Verified** by
  `verify:ui:teacher` (25 assertions) and by reading `lib/server/class-view.ts`.
- The learning record is an **append-only evidence ledger per learner**, and the learner model is a
  *projection* of it. The invariant — "no authoritative learner-state mutation that cannot be
  reconstructed from an evidence event" — is enforced in code and asserted in `npm run verify`
  (**Verified**, 3085 assertions, 0 failed).
- Everything works with **no AI configured**; with a key, the four AI tasks fall back to the offline
  engine on each of the four documented failure modes (**Verified** for the no-key path and the
  engine's fallbacks; **Untested** against a live third-party provider).

**What it is not yet:**

- It is not a **database-backed** product. `OPENMIND_STORE=postgres` is refused, there is no Postgres
  backend file in the tree, and accounts still live in `auth.ts`'s own `accounts.json` outside the
  storage port (§D). Deployments are therefore **single-process**.
- It is not a **reviewed** educational product. **0 of 135 concepts have been read by a qualified
  person, and 0 of 20 national curriculum pathways have a reviewed syllabus mapping** (§E).
- Its global coverage is a **picker, not a curriculum**: 71 country codes are offered, 19 have a
  national route, and 52 are explicitly offered international/independent programmes instead (§E).
- It is not **measurably effective**. There is no outcome instrument and no pilot has started; the
  repository says so itself in `docs/PILOT_SCOPE.md` ("DECIDED by the owner, NOT STARTED").

**The single most important thing a reader should take from this audit:** the engineering discipline
in this repository is unusually high and the *honesty* of its documentation is unusually high — the
published numbers, the known limits and the design rationales are, in the overwhelming majority of
cases I checked, accurate. The gaps are not hidden engineering failures. They are **the gaps the
project itself documents and has not yet closed**, and the most consequential of them are
*educational* rather than *software*: nobody has read the questions, and the measurement instrument
that decides what a learner is taught is still biased toward long and digit-bearing options.

## D. Technical architecture and storage

### D-1 · The tree and what is in flight

Uncommitted (preserved, not touched): 21 modified + 1 new (`lib/server/transaction.ts`). This is the
storage port cutover — the six learner-record routes, `lib/server/{store,storage,storage-file,projection,tutor,microdiag}.ts`,
`scripts/{verify-engines,storage-conformance,compile-engines}.mjs`, `docs/STORAGE_SPEC.md`, `AGENTS.md`,
`README.md`, `audit/*.json`, `next-env.d.ts`. `npm run verify` passes **3085/0** and `tsc --noEmit`
is clean **on this state**, so the in-flight work is coherent as it stands.

### D-2 · One backend is servable

| Backend | State |
|---|---|
| File (flat JSON under `OPENMIND_DATA_DIR`) | **Served.** `lib/server/storage-file.ts`. |
| Postgres | **Absent.** `lib/server/storage-postgres.ts` does not exist. `lib/server/pg.ts` is a connection helper for `scripts/migrate.mjs`. `resolveStoreKind` throws on `postgres`; `lib/server/store.ts` calls it at **module load**, so a misconfigured deployment dies at the door. |
| A typo in `OPENMIND_STORE` | **Refused** (measured: `mode:"unservable"`, `blockedBy:"store_not_implemented"`). |

Migrations `0001`–`0006` exist and are rehearsed by `db:verify` — but the schema is a **parallel
artefact**: nothing in a served request reads it.

### D-3 · What still bypasses the port (the honest remaining inventory)

- `lib/server/auth.ts` — `accounts.json` (+ `session-secret`) via its **own** `withLock("accounts.json", …)` table. Accounts are outside the port and outside the store's lock table.
- `lib/server/erasures.ts` — dir-parameterised by design (`readErasures(dir)`, `appendErasure(dir, …)`, `confirmErasure(dir, …)`, `applyErasures(dir, …)`, `dirErasureTarget(dir)`) and writes `profiles.json`, `papers.json`, `classes.json` directly, because its most important caller is a *restored copy*, not `DATA_DIR`.
- `lib/server/boot-log.ts` — `boots.json` (documented, benign).
- `lib/server/store.ts` — profiles, classes, rooms, packs, papers, personal papers, `ai-cache.json`, `interventions.json`, erasures: still its own functions, behind `readJson`/`writeJson` (temp-file + rename).
- `lib/server/evidence-file.ts` — the one `appendFileSync` in the codebase (the ledger), reached through the facade and exactly one importer.

**Consequence:** `OPENMIND_STORE=postgres` must stay refused — with the profile on files and the ledger
on a database, one learner's record would live in two places. That reasoning is in the code and is
correct. **It also means: today, one deployment = one process.** Two servers over one directory lose
each other's writes, and the README says so plainly.

### D-4 · Transactions (the in-flight work)

`withLearner` / `withLearnerState` hold the profile lock and **stage** the record write; a `fn` that
throws leaves the record as it was. `commitAndProjectIn(ctx, …)` is the only write path inside a
transaction; `lib/server/transaction.ts` is the port-facing door; routes no longer name the port's
`appendEvidence`/`commitAndProject`, and `updateProfile` has been **deleted** (verified: no occurrence
in `lib/server/store.ts`). The guarantee is precisely "the record does not move" — **not** "the ledger
rewinds". An append-only ledger cannot rewind, so a re-sent event id is a no-op and the retry is safe;
callers must be correct under the weaker guarantee. This is documented and tested, and it is the right
call — but it is a real difference from a database transaction and any future reviewer should not
read "transaction" as ACID.

### D-5 · Durability, readiness and the refusal

`lib/env.ts` measures the mount table, refuses to guess, and fails closed. I drove the pure rule
directly (`storeReadiness`, from `.verify/env.js`) — **verified measurements, not inference**:

| Environment | `mode` | `writesPermitted` | `blockedBy` |
|---|---|---|---|
| production, no `OPENMIND_DATA_DIR` | `undeclared` | **false** | `data_dir_undeclared` |
| production + `OPENMIND_DATA_DIR` set | `host-durable` | true | — |
| production on an ephemeral host, nothing declared | `unproven` | **false** | `data_dir_not_durable` |
| production on an ephemeral host + `ALLOW_EPHEMERAL_STORE=1` | `accepted-ephemeral` | true | — |
| development, no config | `host-durable` | true | — |
| production + `OPENMIND_STORE=postgres` | `unservable` | **false** | `store_not_implemented` |

`data_dir_undeclared` is in `STORE_BLOCKING_CODES`, so it blocks writes and readiness, not just a note.

### D-6 · ⚠ The documented install path that cannot save learner work

**Verified** (driving the real rule, row 1 above). The README's non-Docker path is
`npm ci && npm run build && npm start`, and configuration is described as **"all optional"**. `next start`
runs with `NODE_ENV=production`, so the data directory resolves to the default `./.openmind-data`, which
`lib/env.ts` classifies as `data_dir_undeclared` → **every learner-record write answers 503
`store_not_durable`, and `/api/ready` answers 503**. The deployment *looks* healthy (the site renders,
the diagnostic starts) and silently refuses to record anything.

Two things make this worse than a docs typo: the correct paths (`start-openmind.sh`, the Docker image)
**do** export `OPENMIND_DATA_DIR`, so the author never met this; and the failure is a *refusal* rather
than a loss, which means the learner sees an error, not missing work. **This is a P0 for a first-time
self-hoster and a two-line fix** (`OPENMIND_DATA_DIR=$(pwd)/.openmind-data` in the README block, or a
`.env.example` default, plus a line in "Known limits").

> **RESOLVED · 17 Oct 2026.** Fixed as a docs + contract change rather than a default: the README and
> `docs/DEPLOYMENT.md` now declare `OPENMIND_DATA_DIR` **inside** the block that runs `npm start`, the
> "all optional" claims are gone from the README, `docs/DEPLOYMENT.md` and `.env.example`, and
> `STORE_BLOCKING_CODES` is untouched. Two regression checks: a docs predicate in `npm run verify`
> (every documented server-start block must declare a store, or start through a containerised path
> that does) and `npm run verify:install`, which builds the standalone artefact and drives all four
> states through it. Measured live on the built artefact, `npm start`: configured → `/api/ready` 200,
> `POST /api/profile` 200 with the record on disk and `/` served styled; unconfigured → `/api/ready`
> 503 `data_dir_undeclared`, `POST /api/profile` 503 `store_not_durable`, nothing written. **Not
> proved by any of this:** that the store survives a redeploy — that stays the restart drill's job
> (`npm run verify:persistence`), and it is why the failure was a refusal and not a loss.
> Also still true: `.env.example` keeps `OPENMIND_DATA_DIR` **commented** on purpose, because a
> default would claim an arbitrary production directory is durable.

### D-7 · Backup / restore / erasure

Present and unusually careful: `scripts/backup-store.mjs` (manifest + sha256, refuses to write inside
its own source, reports a store that changed mid-copy, refuses to overwrite a backup), and
`scripts/restore-drill.mjs` (six steps: back up → verify → restore byte-for-byte → re-apply the erasure
log → boot the artefact → re-derive a learner). **Untested here** (needs a production build). Its own
header is honest that it does not stop writes during the backup and does not prove a restore onto
different hardware.

## E. Educational quality assessment

This is where the audit's most consequential findings sit, and all of them are **measured on this tree**.

### E-1 · The measurement that decides what a learner is taught is biased

`npm run gate:options` **passes** (11/0) — but read what it is: a *regression floor*, not a quality bar.
The published figure is **84 of 135 concepts have an option-length tell above the 35% line**, and the
best bank-wide strategy across eight fixed strategies (longest/shortest text, length extremes, middle
length, most digits, largest value, first, last) scores **34.0% against a 25% chance line**.

Two concepts are recorded as **"REWRITTEN BUT NOT FIXED"** — `gravity-fields` (88.3%, digit cue) and
`hormones` (82.5%, digit cue) — and one (`ai-basics`, 36.7%) as repaired. The repository's own
`docs/ASSESSMENT_VALIDITY.md` names this as a per-family authoring job on 82 concepts.

**Why it matters more than it looks:** the diagnostic is the instrument that decides which concepts a
learner is taught and at what depth. A learner who never reads the question beats chance by 9 points,
and the effect is concentrated (a *digit* cue at 80–88% on the two concepts measured at the served
level). This is not "some distractors are weak"; it is **the instrument reporting a number that the
instrument's own construction partly produced**.

### E-2 · Nobody has read the questions

| Layer | Count | Source |
|---|---|---|
| Concepts with a structural check (4 distinct options, no float noise, non-empty explanation that states its key) | **135 / 135** | `verify:q`, `audit/verification-coverage.json` |
| Concepts whose answer is **independently re-derived from the prompt** | **5 / 135 (3.7%)** | `verify:q` — the `SEMANTIC` matcher map: `fractions`, `surds`, `completing-square`, `mixture-problems`, `circle-area-arc` |
| Draws checked only structurally | **39 000 of 40 500** | `verify:q` output |
| Concepts **reviewed by a qualified person** | **0** | `audit/item-reviews.json` (`reviews: []`) |
| National pathways whose syllabus mapping has been reviewed | **0 of 20** | `curriculum-gate`, `audit/curriculum-coverage.json` |

`verify:q` states this in its own words — *"That is a measurement, not a clean bill: no matcher exists
for those shapes yet."* A generator can produce four distinct options, a non-empty explanation and a
consistent key while **teaching the wrong thing**, and for 130 concepts this repository has no check
that would notice. The review *workflow* is half-built and correct — `audit/item-reviews.json` is
validated (a claim without a reviewer and a date fails the audit), and `npm run pilot-pack` has already
produced the 11-concept, 110-item pack a teacher would read — but **no reviewer exists and the file is
empty**.

### E-3 · Difficulty and depth are partly structural limits

- **119 of 135 generators declare a single difficulty**, so a curriculum tier can only move the depth of 16.
- The content-ceiling gate passes **276/0**, with **95/95 advanced tier × subject rows REACHED** — so the depth problem has been substantially addressed at the *course* level.
- 8 practisable concepts still carry a content gap; they are the deliberately-low primary arithmetic concepts (`place-value`, `addition`, `subtraction`, `multiplication`, `division`, `order-ops`, `rounding`, `negatives`). Keeping them low is a *test dependency*: the engine suite relies on genuinely low-ceiling concepts existing. Their gaps are reported, not hidden.
- `extended_response` is unreachable for **every** concept and is reported per concept as an instrument limit rather than as a gap in the learner — an honest treatment of a real limitation.

### E-4 · Curriculum and international coverage

| Measure | Value | Honest reading |
|---|---|---|
| Country codes offered in enrolment | 71 | A picker, not coverage |
| Countries with a recorded national route | **19** | US, GB, IE, IN, NG, KE, ZA, GH, TZ, UG, PK, BD, ID, PH, BR, MX, AU, CA, CM (verified from `audit/curriculum-coverage.json`: 19 entries with `status:"national"`) |
| Offered choices with **no** national route | **52** | 51 country codes **plus** the "Prefer not to say" (`XX`) independent route — each explicitly offered `int-igcse` + `int-ib` + `any-independent`, **not** silently defaulted |
| National pathways | 20 | Cameroon has two systems and forces a choice |
| Specifications | 30 (27 national · 2 international · 1 independent) | |
| Pathways with **no structural source on file** | **20 of 20** | Only Cameroon's two pathways cite a source URL |

The honesty machinery here is genuinely good: the picker tells the learner *"Syllabus mapping:
OpenMind's own, not yet reviewed by a subject specialist"* — **asserted in `verify:ui`**. A learner in
Ethiopia is offered IGCSE/IB/independent rather than being assigned someone else's curriculum. The
finding is not deception; it is that **"serves 71 countries" is a claim about a menu, and only 19 of
them have a curriculum anybody has checked.**

## F. Security, privacy and deployment

**Confirmed issues**

1. **No rate limiting, no lockout, no delay on sign-in — admitted in `docs/SECURITY.md` and
   `docs/DEPLOYMENT.md`.** Unlimited password guessing against a known email is possible. For a
   self-hosted school deployment this is a real risk on the first internet-facing instance.
2. **No rate limiting on AI routes.** With a key configured, `/api/ai` and `/api/tutor` are
   unauthenticated-cost surfaces; `ai-cache.json` dedupes identical explanations but is not a quota.
3. **Single-process store, no login throttling, no tenant above classes** — the three limits
   that decide whether a public multi-school deployment is safe. All three are documented.

**Verified protections (strong)**

- Learner data requires a **capability secret** or a session that owns the profile; the id alone is a
  401 (`e2e` asserts this on every learner-scoped door).
- Sessions are **revocable server-side** (a session epoch inside the signed payload) — sign-out really
  ends every device's session.
- Passwords: scrypt, per-account salt; the plain password is never stored or logged.
- Cross-learner evidence writes are refused (`learner_mismatch`); path-unsafe learner ids are refused
  rather than sanitised.
- A **static credential scan** in `verify-engines.mjs` fails any client `/api/…` call that omits the
  secret (with one named exemption), and it was added *before* the async ledger rollout so a missed
  call site fails rather than silently rendering no questions.
- `/api/impact` is unauthenticated unless `OPENMIND_IMPACT_KEY` is set — and `lib/env.ts` reports that
  as a configuration problem for a public deployment.
- **Safeguarding for children is prose, not code.** `docs/SAFEGUARDING.md`, `docs/AI_SAFETY.md`,
  `docs/PRIVACY.md`, `docs/DATA_GOVERNANCE.md` and `docs/INCIDENT_RESPONSE.md` exist and are specific;
  there is **no age gate, no consent flow and no guardian step** — `PILOT_SCOPE.md` names the consent
  flow as a prerequisite that does not exist. No claim of legal compliance is made anywhere, which is
  correct; none can be inferred from source inspection.

**Deployment state**

| Item | State |
|---|---|
| `docker compose up -d` | Config is coherent (volume `./openmind-data:/data`, `OPENMIND_DATA_DIR=/data`, non-root user, standalone output). **Untested here** (no Docker run). |
| `start-openmind.sh` (port 3000) | Declares its data directory and runs `verify-build-assets.mjs` over HTTP, refusing to report success unless every referenced asset resolves. **Untested here** (needs a build). |
| `npm run build && npm start` | **Broken as documented** — see §D-6 (verified). |
| `npm run production-check` | **NOT RUN** — two Next builds + the static bundle; disk guard reported WARN (5.9 GB). This is the one release step still unproven on this checkout, and `AGENTS.md` says the same. |
| `npm run verify:render` | **NOT RUN** — needs a standalone production server on `:3000`; against the dev server on `:4173` it exits 1 with `gate crashed — fetch failed`. |
| Database half of `verify`, `db:verify`, `db:rehearse` | **NOT RUN** — no `DATABASE_URL`; the suite SKIPS with its reason stated. |

## G. Prioritised backlog (P0–P3)

Twenty findings, ranked by impact. Nothing here is invented to fill a list; **fewer than 25 material
findings are supported by evidence**, so there are 20.

### P0 — release blockers

**1 · 130 of 135 concepts have no independent check that their answer is correct, and 0 have been read by a person.**

`audit/item-reviews.json` empty. *Affected:* every learner. *Consequence:* the platform can teach the

learner pilot. *Fix:* run the existing `pilot-pack` review (11 concepts / 110 items) with a real
teacher; extend the `SEMANTIC` map beyond five shapes. *Verify:* `audit/item-reviews.json` non-empty
with reviewer+date; `verify:q` prints a non-zero reviewed count. *Blocks:* real-learner pilot. Not a
public demo blocker.

**2 · The README's non-Docker install yields a production instance that refuses every learner-record write. — FIXED 17 Oct 2026**
*Evidence:* driven truth table, §D-5, row 1 (`data_dir_undeclared` is a blocking code). *Affected:*
every self-hoster following the docs. *Consequence:* a working-looking site that answers 503 to every
answer. *Fix:* declare the data directory in the quickstart (done, in the block itself — **not** as an
`.env.example` default, which would claim durability for an arbitrary directory), and delete the "all

filesystem — that is P0 #5's storage migration, not this finding.

### P1 — essential for a first release

**3 · Option-length/magnitude bias in 84 of 135 concepts** (2 explicitly unfixed, see §E-1). Fix by
per-family option authoring; verify with `npm run audit:options --prefix=held-out:` **and**
`npm run gate:options`.
**4 · No rate limiting or lockout on sign-in, and none on AI routes.** Fix: a per-account/per-IP
counter with backoff; verify with a burst-request test asserting 429 after N.
**5 · Postgres is not implemented and the file store is single-process.** The schema and the connection
layer exist; the cutover (every learner fact through the port, accounts off `auth.ts`, and a
`storage-postgres.ts`) does not. **This is the item that decides whether a school with two servers can
run OpenMind.** Verify with `scripts/storage-conformance.mjs` driven against the new backend.
**6 · Curriculum coverage is a menu: 52/71 countries unmapped, 20/20 pathways without a source, 0
mappings reviewed.** Fix is honest data work: source the pathways you claim. Verify with
`npm run curriculum-gate`.
**7 · No consent/guardian flow before enrolling minors.** Required before any pilot with real children.
**8 · Difficulty variance is limited to 16 of 135 generators**, so tier adaptation is coarse. Not a
defect, but the ceiling of what personalisation can do today.
**9 · The release checklist (`production-check`) has never been proven on this checkout**, and the disk
guard reports WARN. Until it runs green, "release-ready" is a claim about tests, not about a release.
**10 · `verify:render` — the gate that exists because an unstyled page once shipped with HTTP 200 — has
not been run against a production build here.**

### P2 — important enhancements

11 · Explanations are checked for *consistency with the key*, never for whether they **teach**; the

17 · Documented drift: README says 126 generators (actual 135), 52 misconception patterns (actual 53),
