# AGENTS.md — OpenMind

Project knowledge that cannot be recovered by reading the code.

## Repository & environment

- **Not a git repository.** The checkout is an extracted zip (`NON PROFIT`). `git status`/`git diff` fail — track your own edits; don't rely on git for diffs or committing. Piping the failure (`git status --short 2>/dev/null | head`) exits 0 with no output and reads like a clean tree.
- Dev server runs on **port 4173**; `npm run e2e` and live spot-checks need it up. After a Freebuff restart NOTHING is running, and `npm run start` fails (no `.next` production build) — use `npm run dev`. **The shell tool reaps background children on exit**: `(npm run dev > log 2>&1 &)` dies when the command returns, and `nohup … & disown` hangs the call. Working pattern is ONE command: start the server, poll readiness with curl in a loop, run the task, `kill $SPID`, exit with the task's RC.
- One-shot patch/migration scripts live in `scripts/` and are **not** wired into `package.json`. Only `dev`, `build`, `start`, `typecheck`, `verify`, `verify:q`, `e2e` exist.
- **All learner data lives in one directory**: `.openmind-data/` (`profiles.json`, `papers.json`, `personal-papers.json`, `classes.json`, `rooms.json`, `ai-cache.json`, …), overridable with `OPENMIND_DATA_DIR`. It is the user's real data, not a fixture directory.

## Test harnesses (easy to break, hard to diagnose)

- `scripts/verify-engines.mjs` compiles an **explicit list** of `lib/*.ts` into `.verify/` with tsc, then `require()`s them. A new lib module used by any engine test must be added to that tsc command *and* required from `.verify/`.
- That suite fails with `"X declared designed and stable"` when you parameterise a generator without removing it from `CONSTANT_GENS` in `lib/questions.ts` (see `isVariableGen`). Update the registry with the generator.
- `scripts/verify-questions.mjs` has no build step: it transpiles a **hardcoded file list** (using the repo's own `typescript`) into an OS temp mirror, rewriting `./x` → `./x.mjs`. Add any new import of `lib/questions.ts` to its list or it dies with `ERR_MODULE_NOT_FOUND` from `/tmp`.
- The project has **no tsx/ts-node**, and `node --experimental-strip-types` alone fails on extensionless TS imports. The transpile-to-temp-mirror pattern above is the working way to run TS from a plain `node` script.
- `grep 'difficulty:'` across a generator block is **misleading** for judging depth/variety; measure by drawing seeds instead. Only **16 of 135** generators vary difficulty — 119 declare a single value, so tier-band adaptation can only move those.
- **Verification runs write to that live store.** `npm run e2e` leaves profiles behind (their secrets are `e2e-*`, so they are findable), and `/api/my-paper` runs leave personal papers owned by them. After a run, delete those profiles and any paper whose `owner` is gone, backing the file up to `/tmp` first — never leave the user's store full of test learners. `node scripts/cleanup-e2e-store.mjs` does it in one pass (profiles, accounts, ledgers, recent classes/rooms/papers), pins the user's real profile id and refuses to run if the pin is missing — run it after EVERY e2e.
- **Cleanup by secret prefix is NOT enough any more.** The accounts section of `npm run e2e` signs up `e2e-guard-<ts>@example.test`, and an account's profile gets a SERVER-generated secret, so it looks like a real learner. Also delete `accounts.json` entries whose email starts with `e2e-guard-` and the profiles those accounts own (`account.profileId`), plus their papers/personal papers — and never delete a profile the user's own account owns.
- **A run now also writes evidence ledgers**: `.openmind-data/evidence/<learnerId>.jsonl`, one file per learner. Cleanup must delete the ledgers of every profile it removes, or the next `/api/impact` counts deleted test learners as a real population (it walks the ledgers, not the profiles).
- `scripts/e2e-api.mjs` runs in this checkout, so it can and does read `.openmind-data/*.json` directly. The strongest claim about stored data ("no question text is on disk") is only provable from the file, not from an API response. **`/api/profile` GET returns a PUBLIC view with no `progress`** — reconcile the ledger against the MODEL by reading `profiles.json` off disk, whose shape is `{ [profileId]: { profile, progress, ... } }` (`progress` is a SIBLING of `profile`, not inside it).
- `verify-engines.mjs` now also compiles and requires the SERVER modules (`lib/server/store.ts`, `lib/server/evidence.ts`, `lib/server/projection.ts`) to test the ledger on disk and the projection. A new server module used by the cutover must be added to that tsc list AND required from `.verify/`, or the suite dies with a module-not-found from a plain `node` script. It sets `OPENMIND_DATA_DIR` to an `fs.mkdtempSync` dir **before** the require, because `DATA_DIR` is resolved at module load — and it must never point at the real `.openmind-data`.
- **The assertion count only grows and README drifts behind it** (`npm run verify` printed 1075 while README's Verification section still quotes 586). `npm run verify` is the source of truth; re-run it before quoting a number in a new claim, and never edit code to match the doc.
- **The e2e total VARIES between runs with no code change** (352 and 358 both observed on the same tree) — some sections assert per-loop. Read `failed`, never the total, and never "fix" a changed count.
- `verify-engines.mjs` also carries a **static credential scan**: every client reference to `/api/progress|diagnostic|paper|ai|session` must name `secret` within the call, or use the file's own `authQuery()` helper (whose body must contain `secret`). It is deliberately able to fail — do not relax it to make a new page pass; add the secret. `app/papers/page.tsx` is the one legitimate helper exemption.

## Question engine

- `generateQuestionAt(id, seed, min)` means **"at or above min"** — right for transfer, wrong for curriculum tiers: on a generator capped at 0.5, a low tier targeting 0.45 gets the *hardest* available draw. Use `generateQuestionNear` for tier targets.
- `generateQuestion` pads colliding distractors, but only numeric answers get near-miss padding; the structured padders (fraction, coordinate pair) are what keep the four-option contract for non-numeric answers.

## Architecture: files that must change together

- `lib/genome.ts` holds **135** concepts (maths 67 / physics 18 / chemistry 16 / biology 16 / computing 18), stages 0–5. Home-page subject counts derive from `bySubject()` — never hardcode them.
- `lib/specifications.ts` (25 specs / 20 countries + `INT`/`XX`) resolves coverage **against** the genome; `any-independent` is the only spec reaching all 135. Adding a spec means adding `include`/`exclude` ids that exist in the genome.
- `BoardId` lives in `lib/types.ts` as a union **plus** `BOARD_IDS`/`isBoardId` with a compile-time exhaustiveness guard. Do not re-list board ids anywhere else — `/api/profile` once whitelisted them by hand, so a UK/US board could be offered by the UI and silently rejected on save.
- Terminology is applied **only for English delivery** (a translated stem is already local) and must also be applied to the **marking explanation** — prompts rarely contain the mapped words, explanations do. Only `/api/progress` (serve + answer) and `/api/diagnostic` have a profile; `/api/question` has none, so no board or tier applies there.
- **App state is DERIVED, in one place** (`lib/app-state.ts`): `deriveLifecycle` turns `{auth, profileStatus, profile}` into an explicit lifecycle where `booting` is a state and never an absence, `ACCESS`/`accessFor` is the per-route access contract (`public | authenticated | onboarded | diagnosed`, longest-prefix, **unknown paths default to `public`**), and `resolveRoute` returns `allow | boot | redirect` with the learner's destination carried in `?return=`. `components/route-guard.tsx` is mounted ONCE in `app/layout.tsx`, so no page may re-check signed-in/onboarded/diagnosed for itself. Two invariants are asserted over the whole table in `npm run verify` (▸ Where the learner is allowed to be), including "every page directory is classified" — a new top-level page FAILS the suite until it is added to `ACCESS`. `lib/app-state.ts` must stay in verify-engines' tsc list (it is now).
- A gated route's server-rendered HTML is the BOOT SCREEN, not the page (the guard cannot decide before the session probe answers). `scripts/e2e-api.mjs` section 11 checks markup on `/learn/maths/quadratics` and only sees it because the ♿ button and offline bar render OUTSIDE the guard, from the layout. Do not add an HTML-content assertion for a gated page; check a public route (`/solve`, `/about`) or a gated page's API instead.
- **Sessions revoke server-side** (`lib/server/auth.ts`). The cookie is `acc.<epoch>.<exp>.<hmac>`; `POST /api/auth/logout` bumps `Account.sessionEpoch`, so every outstanding token for that account dies immediately — signing out on one device signs out everywhere, which is the point on a shared phone. Three-part (pre-epoch) tokens are still accepted as epoch 0 so nobody is signed out by the change. Consequences: a new token must be minted via `sessionTokenFor(account)` (it needs the epoch), and every auth check must go through `accountFromRequest` — a hand-rolled `verifySessionToken` call accepts a token the learner has already revoked.
- **`claimGuestProfile(guest)` takes the claim as a PARAMETER** because `signIn()` calls `adoptSession()`, which overwrites `localStorage` FIRST: reading the claim at call time names the account's own fresh profile and silently claims nothing, so "bring this device's progress with me" does nothing after a sign-in (sign-up is unaffected — it reads the claim before its request). Any UI that offers a claim must capture `currentGuestClaim()` at mount and pass it.
- Onboarding decides where to go from the profile **the server returns** (`saved = await createProfile/saveProfilePatch(...)`), not from the session captured when the form rendered. After a sign-in that claimed this device's work those are different learners, and the stale copy sent a learner who already had a diagnostic back to sit it again.
- Every authed call needs the profile `secret`; the id alone returns 401. The client self-bootstraps it (`ensureProfileSecret`) and legacy profiles bind the first secret presented. **A 401 here is silent in the harness**: `scripts/e2e-api.mjs`'s `post()` injects the secret automatically, so a browser call site can forget it and every suite still passes while the page shows no questions. The secret rollout once missed `app/learn/[subject]/[concept]/page.tsx` and all of `lib/anon-practice.ts` (the `/solve` + `/try` wedge) — grep client calls for a `secret` key, not for a passing suite.
- **`handle` is optional end-to-end** (onboarding no longer mints `student-NNNN` ids). Making the type optional touches `lib/types.ts`, `lib/client.tsx` (`createProfile` init), `app/api/packs/route.ts` (author stamp) and onboarding together; the teacher/rooms/packs APIs already `??`-guard a missing handle.
- `lib/next-engine.ts#decideNext` is the decision layer, and it answers six questions per action: **what** (`title`), **why** (`reason`), **why now** (`why`, driven by `profile.examDate` via `daysUntilExam`/`urgencyFor`), **how** (`plan`, fitted to `profile.timePerDay`), the **evidence** (`evidence`) and what else is ready. `minutes` is computed as the plan's own cost, so the card can never promise eight minutes and hand over fifteen.
- The engine's `EN_NEXT` table is NOT the English dictionary — it is reached only when a caller passes **no** translator, and every page passes one. A key that lives only there renders as a raw key (`next.why.examNow`) on screen; the harness now asserts every `EN_NEXT` key exists in `en` and in all 15 dictionaries. `/api/my-pack` was passing neither a translator nor a title resolver, so **the offline pack — the artefact for schools with no internet — shipped English recommendations in every language**, concept titles included.
- A misconception is **repairable** (`REPAIR_STREAK` in `lib/learner-model.ts`). The ledger only ever counts up, so using the lifetime count as the REMEDIATE trigger made the repair permanent: fix the slip and the engine still opened with "Fix: …". `ConceptEvidence.misconceptionHits` now means slips still being made; `lifetimeMisconception` keeps the record for the teacher view.
- `lib/session.ts` is the closed learning loop: a session's **baseline** is captured server-side before the first answer and stored on the profile as transient `learnSession`. Every transient server-only key must be added to `publicProfileState`'s strip list — a baseline that reaches the client can be edited, which defeats the point of a measured before/after. `projectionBase` is on that list too (it is server bookkeeping and a duplicate of `progress`, not secret but not the client's business); add yours beside it. Activity (`asked/correct/hint-free/transfer`) is incremented in `/api/progress`'s grading path, never from the request body.
- The concept page opens its session once per concept visit (a `useRef` guard). Without it, `finish()` refetching the profile changes `intent` → `start` identity → the mount effect re-fires and **clears the result panel the learner is reading**.
- **Two credentials are valid, not one**: `lib/server/auth.ts#authorisedProfile` accepts a signed-in session that *owns* the profile, else the capability secret (else the legacy first-writer binding). Every route that acts for a learner should use it rather than re-implementing the check.
- Accounts own exactly one profile (`Account.profileId`). Sign-in hands the profile's **secret back to an authenticated session** — that returned secret is the bridge that makes an existing learner API work on a brand-new device. Do not remove it thinking it is a leak; a session without it cannot call `/api/progress`.
- `POST /api/auth/claim` refuses (409 `account_has_progress`) when the account already has recorded answers: swapping one learner's history for another's silently is the data loss this project must not do. The UI must explain the refusal, not retry.
- `Account.verified` is **false for every account** — there is no mail service. That is a truth to surface in the UI, not a bug to chase.
- Exam papers (`lib/papers.ts`) keep their answer key **server-side** in `papers.json`, keyed by paper id (`saveStoredPaper`/`getStoredPaper`); grade boundaries ride on the key so marking needs nothing else. A paper's answers are recorded with `mode: "independent"` — exam conditions are the independence evidence the learner model is otherwise starved of.
- `lib/llm.ts` is multi-task (tutor · explain · question · mark) and every AI result is validated before use: an AI question failing the four-option contract is dropped and the slot refilled from the deterministic engine. `aiStatus()` is surfaced verbatim in the UI; a missing key gates nothing, and every call returns a REASON when there is no text (`no_key` / `provider_error` / `timeout` / `malformed`) rather than a bare null. See **The online AI layer** (next sections) for the grounding, the disclosure rule and how to run the AI half of the suite.
- `lib/question-bank.ts` is the provenance / pool / exposure layer, and it states one thing the rest of the codebase depends on: **no official board question is bundled** (`OFFICIAL_ITEMS === 0`) because none are licensed. `source`/`provenance`/the pools exist so that adding licensed content is a DATA change, not an architecture change. Never let a surface imply an authored item is an official past-paper question.
- Three pools, and they are not interchangeable: **diagnostic** and **assessment** may never re-serve an item (`isUsable`/`poolAllowsReuse`), **practice** may. A measuring pool that repeats an item lets "you improved" mean "you remembered". Exposure lives on `ProfileState.seenQuestions` (item id → first-served time; re-marking never resets it) and is written server-side by `/api/diagnostic`.
- `buildBlueprint` writes the diagnostic's coverage over the genome's **stage bands**, not board topic names — the specification layer encodes stage windows and concept coverage, not a board's named-topic taxonomy. Inventing "4.3.1 Infection and response" headings would make the blueprint look more authoritative than the data is. `buildBlueprint`/`blueprintConcepts` are deterministic in (spec, subject), so a baseline and its later retest sample the SAME concepts — without that, before→after compares two different tests.
- A diagnostic answer is attributed to a demand band by the difficulty **actually served**, not by the ladder stage that asked for it. A generator with a flat ceiling (e.g. `place-value`, always 0.10) therefore contributes every one of its items to the SAME band, whatever stage it was served at — so "why is this band never measured?" starts with `conceptDepth`, not with the ladder.
- The diagnostic's item seeds are deterministic (`d<startedAt>:<concept>:<asked>:<attempt>`). A `Math.random()` salt made every retry a different test and made a result unauditable.
- Skills: `SKILLS_IN_BANK` is **measured against the generators, not declared**: the bank can produce `recall`, `application` and `multi_step` only. No question declares a difficulty ≥ `SKILL_MIN_DIFFICULTY.data_interpretation` (0.75) and only three concepts reach multi-step at all, so `data_interpretation` and `extended_response` are both `inBank: false`. `▸ The question bank` sweeps every generator and fails if the declaration and reality disagree — move a band back into the bank when a deeper generator lands. `skillQuotaFor` redistributes the unreachable shares rather than saving a slot for them.
- A demand row carries **why it is empty**: `inBank: false` (beyond the instrument), `reachable: false` (no question in THIS course's bank reaches it — a Kenyan junior sample tops out at application level) or neither (this sitting did not get there, which is a real gap). `demandEstimates(session)` computes reachability from `questions.conceptDepth` over the session's own concepts. Without this, an empty row reads as a gap in the learner.
- **Evidence carries its own confidence** (`EvidenceEstimate`, `lib/question-bank.ts`). `value` alone is an over-claim: 2/2 and 6/6 are the same percentage and not the same evidence. The judge is an Agresti–Coull interval (the Wald interval collapses at n/n and would award perfect confidence for two answers). `measured: false` (value `null`) and `value: 0, measured: true` are different claims and no surface may conflate them. Recompute estimates via `estimateEvidence`/`estimateFromProgress` rather than hand-rolling a percentage.
- Two decisions come out of that interval, both one-sided where it matters: `estimateIsDecided` (a probe cannot change the decision, so the blueprint selector does not spend one) and `bandDemonstrated` (the band's interval floor clears evens, so a FRESH concept need not re-prove it). Only the strong direction skips — a band settled weak is still probed on every concept. The skip's standard is deliberately above the ladder's own two-answer band rule, and the result reports `skippedBands`, so a shortened diagnostic is visibly a decision rather than a missing half.
- The blueprint sample is **depth-covered**: `blueprintConcepts(..., depth)` guarantees a concept that can express the deepest band the course can reach. Without it, a sample drawn entirely from low-ceiling concepts reports multi-step as "not measured" for every learner in that course forever — a sampling bug wearing the costume of a fact about the learner. `questions.conceptDepth` is memoised and deterministic.
- Papers are OpenMind's own exam-style questions written to a board's specification and format — **not** reproductions of copyrighted past papers, and the page says so. Never let the UI or README imply otherwise.
- `lib/content-rights.ts` is the rights model, as code: every piece of content carries an ORIGIN (`openmind_authored` · `licensed_official` · `user_provided` · `external_link`) and the origin decides which operations are permitted. `mayUse`/`assertUse` is the single gate, and `assertUse` THROWS — a surface that renders something it may not render should fail loudly, not quietly show nothing. **Licensed material with no licence record on file is granted nothing at all** (`LICENCES` is empty, honestly), an unstated permission inside a record is a denial, and an expired licence grants nothing. `external_link` may only be LINKED: no embed, no mirror, no store. Seeing content is never permission to do anything with it, and "the student uploaded it" is not a redistribution licence.
- **"Bring your own paper"** (`lib/personal-paper.ts`, `POST /api/my-paper`) is the answer to boards whose papers this project may not host: the learner keeps the paper, OpenMind keeps the workspace — question number, marks, marks awarded, and the idea it tested. The route accepts NO content: `validatePersonalPaper` refuses any unrecognised field with `content_not_accepted` and names it, and the route passes the whole body through (not a picked list of fields) so an uploaded document is REFUSED rather than silently dropped. Personal papers are owner-scoped on read (`getPersonalPaper(id, owner)`), private-stored, never shared, never trained on.
- A personal paper runs through the SAME analyser as an OpenMind paper (`analyseMarked`; `analysePaper` is a thin wrapper over it), so evidence is interpreted identically however it arrived. It contributes **no misconception evidence, ever** — a mark total says which idea cost marks, never why — and a question left unanswered is lost marks with `correct: null`, never a wrong answer. `recordAnswer` is called with `mode: "independent"` (a paper is sat without OpenMind's help) and an empty tag list.
- A paper is **diagnostic evidence, not a score**: `lib/paper-analysis.ts#analysePaper` turns a marked paper into per-concept mark losses, `recurring` (an idea that came up more than once — a pattern, not a slip), a `weakest` drill target and `concentration`. It runs server-side in `POST /api/paper` so the client cannot flatter the diagnosis. Unanswered is lost marks but is **never** a wrong answer and never tags a misconception — guessing and skipping are different failures.
- The paper route must pass the answer key's `tags` into `recordAnswer`. With an empty array a paper can say which IDEAS cost marks but never WHY, and the misconception model stays blind to the one thing the mark scheme knows.
- A **specification-built** paper's name is UI and must be translated (`genericPaper(active, subject, lang)` → `subjectLabel`); an **authored** board paper's name is the awarding body's own ("GCSE Biology — Paper 1") and must not be touched. Hence `defaultPaperFor`/`buildPaper` thread `lang`, and the client's paper **list** request must send `lang` too — it once didn't, so "— maths paper" and English subject names leaked into the Arabic picker.

## The evidence ledger (`lib/evidence.ts`, `lib/server/evidence.ts`)

- **The direction is action → event → ledger → projection.** The event is the truth; the learner model is one projection of it. Never "correct" an event — re-project. `projectLearner` must stay order-independent (the harness shuffles the same stream and requires an identical projection), because that is what makes "improve the algorithm, keep the history" possible.
- **THE INVARIANT, and the rule to protect above every refactor: there is no authoritative learner-state mutation that cannot be reconstructed from an evidence event.** If a change to the learner model is not a fold of an event, it is a bug — not a shortcut. A feature that wants to move the model mints an event first.
- **THE CUTOVER HAS HAPPENED: the ledger is the source of truth and the model is a projection of it.** Every write path calls `commitAndProject` (`lib/server/projection.ts`) from INSIDE the profile lock, and the ordering is the architecture: **WRITE EVENT → CONFIRM APPEND → REPLAY → RESPOND.** Routes no longer mutate `state.progress` — `recordAnswer` is now reached only through `foldEvent`, which is what `replayModel` runs. Two consequences you must preserve: if the append throws, the model does NOT move and the route answers `evidence_not_recorded` (503) with the staged question left in place (so a retry works and no answer is silently eaten); and the ledger write now happens inside the profile lock, so the lock order is always **profiles.json → the learner's evidence file** — nothing may take them the other way round.
- **`recordAnswer` is the fold, not the writer.** Do not delete it, and do not let it grow a side door: it must stay a pure function of (state, one answer). `mergeDiagnosticSeed` is the same shared rule for a sitting.
- **A diagnostic sitting folds as ONE event.** `diagnostic_completed` carries its per-concept ladder seeds and folds through `mergeDiagnosticSeed`; its individual `answer_submitted` events are DETAIL, and `foldEvent` deliberately SKIPS `source: "diagnostic"` answers, because the model has never been built from them. Folding both would count every diagnostic answer twice, and an ABANDONED sitting (answer events on the ledger, no sitting event) is the proof the rule is right: the live model never moved, so the projection must not either. The engines suite pins this against `applyDiagnosticResult` — the pre-cutover live math, now kept ONLY as that reference, so do not delete it as dead code.
- **`ProjectionBase` is why the cutover did not eat a pre-ledger learner** (the live store holds one: recorded work, an empty ledger). Replaying an empty ledger over such a learner would reset every mastery to the prior on their next answer. So the pre-ledger model is snapshotted ONCE, lazily, on the first write after the cutover, and `replayModel(events, id, base)` starts FROM it and skips events older than `base.at` (they are already inside it) — 13 recorded answers become 14 instead of restarting at 1. The base is created on a MEASUREMENT, not a guess: `ensureProjectionBase` reconciles a ledger-only replay against the model and only snapshots if something is missing, so a learner whose ledger already covers their model gets NO base and keeps the strongest claim (their model IS the ledger — asserted in verify). `unprojectableShare` names what cannot be rebuilt and `/api/evidence` reports it as `deepReconcile.unprojectable`.
- **The projection rebuilds EVIDENCE state, not identity.** `replayModel(events, id, base, profile?)` reproduces `progress` and `masteries` — every field with an event behind it. The learner's DECLARED facts (subjects, exam, exam date, `timePerDay`, `lang`) are not evidence and no event mints them, so they are an INPUT: `replayModel`'s default shell is a neutral one, and `decideNext` reads `profile.subjects` (which subject to challenge them in) and `profile.timePerDay` (how long a plan may be), so a caller that DECIDES from a replayed model must hand the learner's own profile over or the tail of the ranking silently disagrees. The server door never has this problem — `projectFromLedger` adopts into the LIVE state, and `decisionContextFor` reads the profile off disk — but a test or tool that rebuilds a learner from scratch must pass it `jstate.profile`. Asserted in verify: a replay without the declared profile decides differently.
- **`PROJECTION_VERSION` ≠ `EVIDENCE_SCHEMA_VERSION`.** The schema says what an event MEANS; the projection says how evidence becomes a model. Same history + better projection = better model with no past rewritten, and every projection reports the version that produced it. Bump it when the fold's behaviour changes, not when a field is added.
- **The ledger OWNS some fields; it merely coexists with others.** `LEDGER_OWNED_FIELDS` (attempts, correct, streak, mastery, accuracy, lastSeen, misconceptions, independent, transfer, totalMs, answers) are installed by `adoptProjection`; `LEDGER_ABSENT_FIELDS` (hints, recentHits, microDiag, starter, peer, diag) have no event behind them yet, so they are PRESERVED from the live entry — as are whole entries the ledger says nothing about. Adopting a field the ledger cannot reproduce would delete a learner's hint/starter/peer record on their next answer. `adoptProjection` iterates the FOLD's own keys so a ledger-complete learner's model is byte-identical to a replay of their ledger.
- **One answer, one clock.** Every write route passes the SAME stamp to the event it mints and the projection that follows (`answerEvidence`'s `at`; the diagnostic's sitting-level `at`). Skip it and `lastSeen`/`masteries` stop being reproducible — parity fails by construction. `reconcileDeep` compares the full derivable surface; verify pins zero divergence across a five-stage journey (diagnose → practise → prove → transfer → retain) and the e2e asserts it over HTTP via `GET /api/evidence`'s `deepReconcile`. Don't add compared fields silently — extend `COMPARED_FIELDS` and the journey together. Prefer `replayModel`+string equality over `reconcileDeep` alone when you add a field, or a field the list forgot goes unnoticed.
- **`diagnostic_completed` carries `seeds`** (per-concept ladder counters, validated in `validateEvent` — bad seeds are refused, and replay re-derives mastery via `ladderMastery` rather than trusting carried numbers). Papers (both routes) and micro-checks now mint `answer_submitted` events; personal papers force `provenance: "device"` (the server did not watch the owner's marking). Starter/peer progress creation uses `emptyProgress()` — creating an entry is not a measurement, so mastery starts at the 0.2 prior, never a fabricated 0.
- **`ProfileState` has no `id` field** — the id is the key in `profiles.json`. Use the request's `body.id` (the id `updateProfile` resolved) as `learnerId`; `state.id` does not exist.
- `withLock`, `locks` and `DATA_DIR` are exported from `lib/server/store.ts` so the ledger shares the ONE lock table. A second table would let an evidence append and a profile write race on the same learner.
- **Provenance is stamped, not believed.** `validateEvent` forces `provenance: "device"` on anything arriving over the wire *whatever the body says*; only `answerEvidence()` mints `"server"`. The impact report counts device-reported events separately and says they are unverifiable — keep that true if you add an ingestion path.
- **A `hint_requested` event must NOT add to the concept hint tally.** The hint count attached to a graded answer is authoritative (the server kept that ledger while the question was served); counting the live hint actions too double-counts every hint. `hint_requested` feeds `totals.hintActions` only — `foldEvent` ignores it, and the hint route mints it with `hintEvidence()` so the ACTION is in the history even though the tally is not. That asymmetry is deliberate: do not "fix" it by folding hint actions.
- `reconcile()` compares only the fields BOTH sides keep (and skips `independent`/`transfer` when the model has no such bucket) — noise here would get the check switched off, which is how a reconciliation stops protecting anything. The harness runs a real `recordAnswer` stream through it and requires **zero** divergences, then tampers with the model to prove the check fires.
- **`/api/progress`'s answer action takes `choiceIndex`; `/api/diagnostic`'s takes `chosen`.** Using the wrong name returns a plain 400 `bad request` with no hint about the field, and the e2e section that tries it will simply stall.
- The ledger is wired into the evidence producers (the practice answer path, the diagnostic, papers, and offline sync — the client answer paths go through `lib/sync-queue.ts`, which holds an answer the server cannot take and replays it through the same route on reconnect; e2e §19 proves the server-side half of that). `GET /api/impact` is aggregate-only by construction (`containsIndividualData: false`). A learner with no baseline is `assessed: false` and no later measurement is `null` — never 0 — and such learners are excluded from the change denominator, not counted as unchanged.
- **The teacher's roster reads the ledger, not a claim.** `GET /api/classes` derives each member row server-side via `lib/server/class-view.ts` (`projectLearner` over the member's own events) and returns it as `cls.live`; the stored `students` map is only the member's last self-report, and the report action cannot touch the live view (source tripwire in verify). `/api/pack-export` builds its plan from the same live view and is member-gated (401/403 like the roster) because it carries the answer key. Membership lives in `lib/server/class-membership.ts`: a class read answers only a profile in `cls.members` (or, for pre-`members` rosters, the handle they joined under), and the creator is made a member at create. Students join from `/account` with the code. What no ledger measured is absent from the row — never a 0.

## Evidence → experience (`lib/evidence-view.ts`, `lib/next-engine.ts#decideNext`, `components/evidence-drawer.tsx`)

- **ONE DOOR, ONE DECISION (`lib/decision.ts`).** Every surface that asks "what next?" assembles a `DecisionContext` (the model AND the ledger it was projected from) and calls `decide`/`decideOne` — never `decideNext` directly. verify enforces both halves: a SOURCE check fails the build if any file under `app/` or `components/` contains `decideNext(`, and the engines suite asserts that the live model, a from-scratch replay of the same ledger and the server route door all produce the SAME action — same kind, target, reason, plan and citations. Two surfaces that disagree about the same learner is the failure mode this exists to make impossible.
- **`basis` has FIVE states, and each is a different sentence.** `cited` (this action cites events that must resolve in the context's own ledger), `unattributed` (evidence exists but this rule hinges on no single event — a rest day), `no_evidence` (the ledger is EMPTY **and** the model holds no recorded work: the only state in which "no answers recorded yet" is true), `unrecorded` (empty ledger, but the MODEL holds recorded attempts — a learner who predates the record, and the live store holds one), `unknown` (this SURFACE does not have the ledger). `basisViolations` pins each state to the fact that licenses it and is asserted empty for every real context, with three planted lies required to be REFUSED — the states are not decoration. Never derive it from `evidenceIds.length`: dropping the ledger must cost an action its CITATIONS, never invent a claim about the learner.
- **THE JOURNEY IS THE TEST (`scripts/e2e-api.mjs` §14).** One learner runs diagnose → practise → prove → transfer over the real routes, and after EVERY stage three things are asserted: the decision API and the second surface (the offline pack, decided in its own request) name the SAME work; every citation resolves in that learner's own ledger; and `deepReconcile` still rebuilds the model from the ledger alone. It also pins the wiring that makes the loop honest: the session's `previousStep` (its opening plan) equals the decision the learner was shown, and the plan the session CLOSES with equals what `GET /api/next` serves immediately after — one decision, not two. Retrieval is deliberately NOT in this list: the RETRIEVE rung needs evidence that has aged, so it stays in the engines suite where the clock is fixed, rather than being faked with a `lastSeen` nobody earned.
- **Two HTTP facts that cost a debugging round each.** `/api/diagnostic`'s answer response carries the next question as **`next`**, not `question` — a loop that reads `r.body.question` silently ends the sitting after one answer and looks like a passing (but vacuous) test, so assert the number of concepts measured. And transfer credit is granted only when the server's own transfer layer produced a DIFFERENT surface: a concept whose bank can only re-draw its question is recorded as ordinary work (`mode: independent`), which is why the transfer stage uses a re-framable concept (`linear-equations`) and why the engines suite asserts the surface rule directly.
- **A ledger in flight is not an empty ledger.** Client surfaces use `decisionContextFrom(model, ledger)` and pass what they have; while the fetch is pending the basis is `unknown`. `decisionContext(state, ledger?.events ?? [])` is the banned shape — it turns a network fact into "this learner has no evidence", which the card renders as "No answers recorded yet" for a learner with three hundred of them. verify greps `app/` and `components/` for `?.events ?? []` and fails if it reappears. A server route always holds the ledger (`decisionContextFor`), so it cannot produce `unknown` at all.

- **The engine owns the reasons; React only renders them.** `decideNext` returns `evidenceIds` + `expectedOutcome` with its reasons; verify greps the components for reason literals and fails if any appear. When adding an action kind, add its reason and outcome keys to `lib/i18n.ts` (verify checks every key in the `en` dictionary) — the drawer then shows `BECAUSE / BASED ON / AFTER THIS` from the decision, never re-derived.
- **`/api/evidence-summary` is the display door; `/api/evidence` is the raw one.** The summary speaks experience (dimension bands, recents with `offline` provenance flags) and must never leak ledger vocabulary — the e2e asserts no `schemaVersion` in its response. Dimension rows are `null` when nothing of that kind was attempted: that is *unknown*, not zero, and `measured: null` on an unprobed concept is the same rule.
- **`lib/evidence-view.ts` is the only event-id → text translation layer.** `citationsFor` turns `evidenceIds` into human-readable citations (`basedOn` for counts); no component reads `EvidenceEvent` directly.
- **The Mind pages answer the learner's own question (`/mind`, `/mind/[conceptId]`).** They exist because "why am I doing this?" deserves the record, not a slogan: `what we know` (dimensions), `the evidence` (the answers themselves, including the diagnostic that first made the concept look weak), `why this is next` (the engine's reason/why-now/plan/expected outcome, rendered inline when this concept IS the top action) and `what changed` (the last session on that concept, with the session engine's `changeReason`). Rules verify enforces at the source: no `next.reason.`/`next.title.` literals, no `misconceptionHits`, must call `loadLedger(` (they speak about EVIDENCE, not the mutable model), must never write `?.events ?? []`, and must claim NOTHING about knowledge until the ledger is in hand — "we have not read your record" and "you have demonstrated nothing" are different sentences and only one of them is honest. `/mind` is classified in the access contract (`onboarded`, like `/progress`), so a new page directory is never public by accident.
- **`basedOn` and `conceptKnowledge` answer DIFFERENT questions — do not merge them.** `basedOn` (the drawer) answers "what has MEASURED this learner?", so its first row is the diagnostic/paper subset. `conceptKnowledge` (the concept page) answers "what do we know?", so its first row is EVERY recorded answer, with a `from` field naming the slice each row counts. Merged into one, a probe learner with five correct practice answers on `fractions` showed "Application 5/5" beside "Recall: not yet measured" — as if five recorded answers were not recall. verify pins both directions: practice-only work measures `recall` in `conceptKnowledge` and leaves it empty in `basedOn`.
- **The ladder is pinned by deterministic tests in verify** (fixed `now`, fixed seed): no evidence → DIAGNOSTIC; two wrongs → EXPLAIN; a correct after → PRACTISE; mastery ≥ 0.75 with the right mix → TRANSFER; backdated work → RETRIEVE. The boundary sits between the 4th and 5th correct in a clean stream — one event flip across it must flip the decision. Guided-only rehearsal leaves `independent` **null** (guided is not independent evidence) — if you retune the model, update the ladder's anchors with the probe script, not by guessing numbers.

## The online AI layer (`lib/llm.ts`, `lib/tutor-context.ts`, `lib/server/tutor.ts`)

- **AI explains, hints, adapts and generates practice. It never writes.** Nothing on the AI path imports `answerEvidence` / `hintEvidence` / `appendEvidence` / `commitAndProject` / `updateProfile` / `saveProfile` / `withRetentionProof` — the only route into the ledger or the model is append → confirm → replay/adopt (`lib/server/projection.ts`), reached from the grading routes after the SERVER has marked against the engine's own key. A model's text is returned to the caller and to nobody else. `▸ AI explains, never records` (engines) asserts both halves: a source tripwire over the five AI modules, and a runtime check that a whole exchange — six turns, every fallback included — leaves the ledger file byte-identical and every mastery field untouched. If a change needs a write from an AI path, the change is wrong.
- **The tutor's input is the decision the surfaces display.** `lib/server/tutor.ts#tutorGroundingFor` reads `decisionContextFor` → `decide(ctx, { max: 6, tt, title, now })` — the same door, options and clock `/api/next` and Home use — and hands the model the action, its reason, its citations, its basis, the projection version, what has been MEASURED about the concept (counts, never a 0% for something unasked) and the belief patterns the learner's own answers **on that concept** triggered (per concept, deliberately not `misconceptionHits(state, subject)`, which would attribute an algebra slip to a fractions question). The request body may name the concept the learner opened — the `focus` — and nothing else: it cannot name the decision, the reason, the ids or the version. `▸ AI explains, never records` compares the grounding field-for-field against `decide`'s own output, then reads the prompt back off a stub provider and requires the reason, the cited event ids and `projection vN` to be in it; section **17** of `scripts/e2e-api.mjs` does the same over HTTP against `/api/next`.
- **The fallback is an outcome, not an error page.** `lib/llm.ts` transport returns `AiOutcome`: text, or one of four named reasons — `no_key`, `provider_error`, `timeout`, `malformed`. All four are exercised against a REAL HTTP endpoint (`scripts/ai-stub.mjs`), because the timeout lives in the transport and a mocked `fetch` would not prove it. In every case the offline Socratic engine replies, in the learner's language, and the payload carries `answerSource` + `labelKey` + `aiUnavailable`.
- **A learner is never told a model spoke when it did not.** `disclosureKey` (`lib/tutor-context.ts`) derives the line from `answerSource` and REFUSES the AI key on any payload whose source is not `"ai"` — an escalated label is not a rendering bug this project can have. Three keys, in all 15 dictionaries: `tutor.aiNote` (a model answered), `tutor.fallbackNote` (a model was configured and did not answer), `tutor.offlineNote` (no model on this deployment). `tutor.whyThis` renders the decision's own reason under the reply, and the tutor screen shows no banner about which tutor is running until a reply has said so.
- `/api/tutor` is an OPTIONAL-auth door: given `id` + `secret` it is grounded in that learner; a wrong secret is a 401 (never a silent downgrade to a concept-only turn); a signed-out visitor gets the concept and no claims about anybody.
- **Assigned work stores concepts and a deadline — never progress.** `Assignment` (`lib/types.ts`) lives on the `ClassRoster` (class state, not a parallel store) and carries `conceptIds`, `createdAt`, `dueAt` and the curriculum it was drawn from. Everything a teacher or student reads about it — completion, accuracy, weaknesses, misconceptions, whether to intervene — is DERIVED per member from that member's own evidence ledger over the window `createdAt` opens (`lib/server/assignment-view.ts#deriveAssignmentProgress` / `monitorFor`), so there is no counter to drift. The window reads `e.at` (the server's clock) and never `deviceAt` (the device's claim), which is what stops an offline answer being backdated into an assignment it never counted towards. `▸ Assigned work is derived, not counted` (engines) pins the window, the absent-not-zero rule, the named reasons and a source check that the stored interface has no progress field; e2e section **20** drives teacher → invite → set → complete → monitor over HTTP plus the negative cases.
- **The assignment door has TWO questions, and they are different.** `isMemberOf` licenses a member to read their OWN row; only `isTeacherOf` (`lib/server/class-membership.ts`, written once) licenses setting/removing work and reading the monitor. `GET /api/assignments` is scoped by OWNERSHIP: `assigned` carries the caller's own row for classes they belong to, `monitor` exists only for classes they own — there is deliberately no "get the class's assignments" shape that hands every member everybody's progress. The class declares its `subject` (and optional `specificationId`) at creation; candidates come from `assignableConcepts(subject, spec)` and a class that declared none is asked for one rather than given a default curriculum. `ownerId` (the creator's learner id, never the role label `teacher` or a joiner-chosen handle) is the authority.
- **Modules in the compile mirror must use RELATIVE imports.** `scripts/verify-engines.mjs` compiles its file list with `tsc <files> ...` and NO tsconfig, so `paths` does not apply and `@/lib/...` is `TS2307` for the file that uses it (`class-view.ts` and `assignment-view.ts` were both switched to `../evidence`, `../types`). App pages and routes resolve `@/` normally via Next — only the mirrored `lib/**` files are affected.
- **A study room's tutor goes through the same door, with an HONEST FOCUS.** `lib/server/room-tutor.ts` resolves the focus — the room's declared concept, else a concept the message names from the room's OWN subject, else nothing — and only then calls `tutorTurn`, so a configured model answers in rooms too and the reply carries `tutorSource` / `tutorLabelKey` / `tutorUnavailable` onto the message. Two defects this replaced, both reproduced live: `room.conceptIds[0] ?? "linear-equations"` taught a MATHS concept in every room that declared none (a GCSE Physics room answered "why does the ball accelerate?" with balance-scale coaching), and the room called `socraticReply` directly, so it never consulted a model at all. With no focus the tutor says it does not know which idea is meant, names the subject and asks (`rooms.focusAsk`, all 15 dictionaries) rather than guessing one. Grounding is CONCEPT-ONLY by construction — a room is shared, so a turn must not carry one member's private record into it; `/tutor/[concept]` is where a turn is grounded in a person. `▸ AI explains, never records` covers `lib/server/room-tutor.ts` and `app/api/rooms/route.ts` in the source tripwire, and e2e section **7** asserts the no-focus, named-focus and cross-subject cases over HTTP.
- **Every tutor sentence is a key, in every dictionary.** `lib/socratic.ts` resolves its opening lines from an array, so a missing key is invisible to a `t("…")` scan: English had lost all five `soc.opener*` and twelve other `soc.*` lines to inline code fallbacks, the opener array came back EMPTY, and every default reply collapsed to one fixed paragraph — a learner typing three different things read the same reply three times. The `▸ Internationalisation` sweep now requires all fifteen dictionaries to `define every Socratic sentence`, asserts that forty different questions do not all produce one reply, that the same question twice does, and that a wordless message ("xx") gets an honest request for the question (`soc.askQuestion`) instead of a lecture. The opener index is derived from `(concept, message)` — varied across messages, reproducible for one — never `Math.random()`, which had made the reply impossible to compare with itself.
- `OPENMIND_AI_BASE_URL` + `OPENMIND_AI_KEY` select a self-hosted OpenAI-compatible endpoint and take precedence over the vendor keys — a deployment running its own model must not be shadowed by a stray key in the environment, and it is also what makes the four failure modes testable rather than mocked.
- Running the AI half of the suite: `node scripts/ai-stub.mjs` (logs every request), start the dev server with `OPENMIND_AI_BASE_URL=http://127.0.0.1:8791/v1/chat/completions OPENMIND_AI_KEY=dev OPENMIND_AI_MODEL=stub OPENMIND_AI_TIMEOUT_MS=1500`, then `OPENMIND_E2E_AI=1 OPENMIND_E2E_AI_KEY=dev OPENMIND_AI_STUB_LOG=/tmp/ai-stub.log npm run e2e` (the suite cannot read the server's environment, so `OPENMIND_E2E_AI_KEY` is how it compares the credential on the wire exactly rather than by length). Start the stub AND the server in the same shell as the run: a background process launched in an earlier agent call does not survive here, and a dead stub reads as `provider_error`, which looks like a product bug rather than a harness one. Without those the suite exercises the no-key path and says so in its output; with `OPENMIND_E2E_AI=1` against a server that has no model configured, section 17 FAILS rather than skipping, so an "AI run" that proved nothing cannot report success.

## On-device AI (`lib/local-ai.ts`, `lib/local-model.ts`)

- The ladder's upper rungs are **capability reports with no bundled model**: a `wasm`/`gpu` plan has `model: null` and `downloadKiB > 0` by design. Never let a surface imply a model is present. The shipped rung is `lite` (the fitted classifier), which needs no download/WASM/GPU and therefore runs on the 2016-class phones this project targets — that is why `chooseTier` returns `lite` for almost every device, and only `none` for engines older than typed arrays.
- `PROBE_MODULES` are hand-encoded WASM bytes (a plain module and a SIMD one) and the harness asserts both are valid — invalid bytes would report "no WebAssembly" on every device in the world, silently. The CPU bench is calibrated against a reference of **~2620 kOps/ms** (Apple-silicon laptop); a hidden/backgrounded tab is throttled and measures far lower (observed live: 426), which errs toward `lite` — treat the top rung as a floor, not a ceiling.
- The benchmark **understates**, never overstates, so a device can be under-ranked but never handed a model it cannot run. `probeWhenIdle` exists so the audit never sits in front of first paint.
- The concept matcher deliberately does NOT use the local model: an NB fitted on the matcher's own corpus was measured out (0 promotions on 20 realistic questions — a bag-of-words model cannot beat the scorer that already embodies that corpus, and on signal-free text every posterior is noise with a respectable internal ratio). Use it for tutor INTENT, where it measurably helps. The reasoning is recorded in lib/matcher.ts so nobody re-adds it.
- `classifyIntent` enforces `ANSWER_STRICT` **inside the model's own contract**: "give me the answer" triggers a refusal, so that one label is held to a much higher bar than the rest. Any new consumer inherits it — do not re-implement the threshold at a call site.
- Intent is an **additive fallback**: lib/socratic.ts applies its keyword lists FIRST and only consults the model when no keyword matched, so the model can add recall and can never override a rule that already decided. The harness asserts both directions (a keyword-free wording gets the stuck scaffold; a plain concept question is not misread).
- A fitted model's held-out set must differ in **tokens**, not just wording: bag-of-words generalises by tokens, so re-worded copies of training sentences prove nothing. The intended claim is "never confidently wrong" (abstention is free), not raw accuracy.

## i18n

- 15 dictionaries in one file, declared `const xx: Dict = {` (Bengali is `export const bn`). **The Filipino dictionary's variable is `tl` (Tagalog), not `fil`** — a patch script keyed on `fil` aborts at 14/15 with the misleading `unhandled: tl`.
- Dictionary count is **15**: en, es, fr, pt, ar, sw, hi, id, tl, de, ja, zh, fa, ur, bn. `en` deliberately has no `cn.*`/`cb.*`/`mc.*` keys — the genome is the English source. A missing key renders English text; raw keys appear only when *no* dictionary has the key.
- Duplicate keys in a `Dict` literal are a **TS error**, so patch scripts must be idempotent or the build breaks loudly.
- Anchor inserts on the `const xx: Dict = {` declaration line — the closing `  };` anchor is ambiguous (it also matches `DICTS`).
- Idempotency checks must be scoped to that dictionary's own block; scanning the whole file makes the first patch hide every later dictionary from itself.
- A dictionary's body ends at the **last `  };` before the next TOP-LEVEL declaration** — not "the last `};` in the line range". For the final dict (`bn`) the range runs on through `LANGS`/`LANG_CODES`/`DICTS`, so the naive anchor inserts the keys *inside the DICTS registry* and the only symptom is `Type 'string' is not assignable to type 'Dict'` at the DICTS literal. Indentation is mixed (`  };` for dictionaries, `};` column-zero for `DICTS`), so match on the declaration boundary, not on indentation alone.
- The header above the first dict (`Dict`, `LangMeta`) sits in the first dict's line range: a patch script that rebuilds the file from per-dict slices silently deletes it, and the failure reads `Cannot find name 'Dict'` at line 1.
- Render concept text through `ctitle()` / `cblurb()` / `mcName()` / `mcCoaching()` (`lib/content-i18n.ts`). Printing the raw genome field (`getConcept(id).title`) is the most common English leak, and it survives every hardcoded-string sweep because it is a variable, not a literal.
- Keys reached only through a variable or a data array (`path.*`, `acc.b.*`, `proj.*`, `tr.*`) are invisible to `t("…")` greps: audit by extracting all key-shaped string literals and diffing them against the `en` dictionary. A key defined in *no* dictionary renders its raw name in **every** language, English included.
- Check parity by counting key-shaped literals per dictionary. The `bn` dictionary once shipped 242 UI keys short because it was added after the others.
- `decideNext(state, max, tt, title)` takes a concept-title resolver: pass `(id) => ctitle(lang, id)`. Without it the next-step engine composes English concept names (`Practise: Negative numbers`) inside an otherwise fully translated next-step card.
- A patch script anchored with `/^\s*"key":/` reaches only the dictionaries that put that key FIRST on its line, and much of `lib/i18n.ts` packs several keys per line — `diag.done` is first in just 4 of 15, so the script aborted at "4/15" rather than half-writing the file. Guard scripts with an `inserted === 15` throw BEFORE the write, and prefer `line.includes('"key":')` over a line anchor.
- Keys that surround an inserted number (`next.reason.practisePre` / `…Post`) carry their own punctuation — `Post` starts with `%`. A template that adds another `%` ships `44%%`; the engine suite now rejects doubled percents, doubled spaces and unfilled `{placeholders}` in engine output.
- Counts are interpolated with `fill(t(key), { n, m })` (`lib/i18n.ts`), not by concatenating translated fragments — word order differs (`第{n}問／全{m}問`).
- There is no plural machinery, so a count that can be 1 needs its own key (`an.qsOne` beside `an.qs`, `own.savedOne` beside `own.saved`) — `{n} {t("an.qs")}` shipped "1 questions".
- The paper grade band **"Pass"** is a word, not a symbol: it needs `pp.gradePass` ×15. `A*`/`A1`/`9`/`500` are symbols and stay as data.
- Coaching (`mcp.<id>`) is authored English in **no** dictionary, while all 14 non-English dicts carry every `mc.<id>` (52), `cn.<id>` and `cb.<id>` (135 each). Use `mcCoachingNative()` inside a translated sentence: it returns `""` for a language with no native line so the caller drops the clause, instead of splicing an English paragraph into the middle of, say, an Arabic one. Use `mcCoaching()` only where English-in-English is acceptable.
- Reaching a key through a template literal (`t(`plan.${p.kind}`)`) makes it invisible to every `t("…")` grep: enumerate the possible values in the harness instead.
- A key-parity audit must scan each dictionary **body** with an unanchored regex (`/"([a-z0-9._]+)":/g`). A line-anchored `/^\s*"key":/` matches only the FIRST key on a line, and much of `lib/i18n.ts` packs several keys per line — that audit reported 235 phantom gaps when the real count was zero.

## User preferences (stated in session)

- **Any UI text change must be translated into all 15 languages** — "don't leave any English unless necessary". Proper nouns (exam/board names, grade labels like "Form 4") stay as data, not translation keys.
- **Never fake capability.** Represent scaffolded or unimplemented behaviour honestly in the UI *and* in README claims; the user explicitly values honest limits over cosmetic polish. When a feature is only scaffolded, the UI must say so rather than imply it works.
- Prefer a real fix plus a permanent harness assertion over patching symptoms.
- **The stated product principle, verbatim**: every learner action must produce evidence; every meaningful piece of evidence must be able to change the learner model; every learner-model change must be able to change what OpenMind recommends next. `▸ The evidence contract` in `scripts/verify-engines.mjs` asserts that chain end to end — treat a failure there as a failure of the product claim, not of a helper.
- **Retention is a measurement, not a schedule.** A concept is served as a *retrieval* only when the scheduler (`lib/retention.ts#isRetentionDue`) says its interval has elapsed — the client never declares it — and the answer then counts as retention evidence only if it was hint-free AND at least a day after the previous evidence on that concept (`lib/progress.ts#recordAnswer`, mirrored by `projectLearner` so the ledger alone rebuilds it). A FAILED delayed recall counts as asked-but-not-correct (forgetting is the signal the dimension exists for); a same-sitting repeat and a hinted retrieval count as neither. `▸ Retention is measured, never assumed` (engines, fixed clock, incl. the `sess.r.retained` reason existing in all 15 dictionaries) and section **16** of `scripts/e2e-api.mjs` (HTTP, using aged device-reported evidence as the only honest way to age a ledger) pin it. Never reintroduce a surface that reports retention as "not yet measured" unconditionally — `/progress` did, and it lies once the learner has earned it.
- **The content→model coupling is asserted as a PAIR, not only as a journey.** `▸ Two learners, one bank, different evidence` (engines) and section **15** of `scripts/e2e-api.mjs` enrol two learners on the same specification and serve them the same concept (engines: the identical draws, by seed; HTTP: the same bank per learner), with the answers as the only difference, and require: (a) dimension rows that differ only as the evidence says, (b) every dimension the history did not measure reading `unmeasured` with `rate === null` — no evidence is never a weakness, on the concept or off it, and (c) a different `NextAction` from `decisionContextFor` + `decide`, the `/api/next` path itself. A same-history twin is the control: identical decisions field for field, except each learner's citations come from its own ledger. Evidence is recorded through `updateProfile` → `answerEvidence` → `commitAndProject`; never assign a model field to make one of these pass.
- The milestone the architecture exists for is asserted as ONE learner's chain, in two places: `▸ THE PROOF` (engines) and section **5d** of `scripts/e2e-api.mjs` (HTTP). Baseline measurement → the plan targets what it found weak → hint-free work on it → **the plan moves forward** → a later, parallel-form sitting measures the repair on the same band → the plan reflects it. Both include the CONTROLS that make it falsifiable: no new evidence ⇒ the plan is unchanged, and failing the same work moves the plan the other way. Never weaken those controls to make a change pass.
- The competitive frame the user chose: **not** "Educake but with more features". Differentiation is the learner model, past papers as measurement instruments, explicit misconception/transfer/independence tracking, and the "why am I doing this?" narration. Volume of questions is explicitly NOT a moat, and the user's own stated danger is **overbuilding** — a feature catalogue is worth less than an excellent loop.
- The user's long-term direction: OpenMind as an adaptive platform across subjects, curricula, boards, languages and countries (Dr Frost-style depth), positioned as learning infrastructure rather than another chatbot.

## Preview tooling quirks

- A client-side navigation does **not** remount `I18nProvider`, so writing `openmind:lang` to localStorage needs a full reload to take effect.
- `preview_screenshot` can capture a stale frame after a navigation; trust `preview_snapshot`/`preview_evaluate` over an immediate screenshot. It also fails outright (`no frames`) when the webview is not composited — `reload` does not fix it, and a reload discards in-page session state.
- `register_preview` refuses a second registration for the same server unless `replace: true`.
- `preview_evaluate` calling `history.back()` **destroys the execution context** (`Preview bridge error (cdp_error): Execution context was destroyed`) and the return value is lost — the navigation still works, so re-evaluate afterwards to read the new state instead of retrying the same expression.
- `preview_evaluate` has a **10s** wall clock and does not tell you that a `click()` already fired a `fetch`: a form-submit style flow can complete *and* time out. Drive long flows as separate small evaluations instead of one async block.
- React-controlled inputs ignore a plain `el.value = x`: set through the prototype descriptor (`Object.getOwnPropertyDescriptor(el.constructor.prototype, "value").set`) and dispatch `input` + `change`, or the state never updates and the next step looks broken.
- `npm run e2e` can fail with `ECONNRESET` when the dev server is recompiling (a new file triggers a rebuild that can restart it mid-run, sometimes with a new PID); re-run it before believing a regression.
- The exercise/diagnostic pages are **two-step**: a question needs a `button.choice` click AND then a separate "Next question →" click. A driver that only clicks choices stalls forever on the feedback panel; a working loop clicks the Next button when present, otherwise a choice.
- Drive such a flow as ~3–4 steps per `preview_evaluate` call (≈200ms between), and remember a full baseline is ~16–20 questions — budget the calls, or verify the report from the engines instead.
