## 1. Current architecture

- **Runtime:** Next.js 15 App Router, React 18, TypeScript. No test framework —
  the gates are Node scripts under `scripts/` driving a compiled mirror of
  `lib/` at `.verify/`.
- **Engine layer (`lib/`, 58 modules):** the knowledge `genome`, question
  generators (`questions.ts`, `questions-deep.ts`, `questions-senior.ts`),
  the diagnostic (`diagnostic.ts`), the learner model (`learner-model.ts`,
  `progress.ts`), the append-only evidence ledger (`ledger.ts`, `replay.ts`,
  `server/projection.ts`), the single decision engine (`decision.ts`,
  `next-engine.ts`), retention (`retention.ts`), proof vocabulary
  (`proof.ts`), the offline matcher/tutor (`matcher.ts`, `socratic.ts`), i18n
  (`i18n.ts`, 15 languages), and the AI layer (`llm.ts`, `local-ai.ts`,
  `local-model.ts`, `tutor-context.ts`).
- **Surfaces (`app/`, 26 pages + 30 API routes):** landing, onboarding,
  curriculum, diagnostic, learn (subject + concept), solve, try, tutor, mind,
  progress, mistakes, papers, offline, rooms, projects, teacher, dashboard,
  hub, account, about, help, access, genome.
- **Static twin (`docs/`):** a second, browser-only build of the same engines
  (`openmind.engine.<hash>.js`) plus a single-file `openmind.html` that runs
  from `file://`, with a service worker (`sw.js`). `docs/app.js`,
  `docs/app.css`, `docs/index.html` are hand-written; everything else in
  `docs/` is generated by `scripts/build-static-app.mjs`.
- **Audit harness (`audit/`):** baseline JSON + probe scripts
  (`engine-audit.mjs`, `regression.mjs`, `ui-audit.mjs`, `stage1-report.mjs`).

The evidence-ledger → deterministic-projection architecture is the spine of the
product and is **preserved**. Nothing in this audit proposes replacing it.

## 2. What demonstrably works

- **Grading and evidence.** An answer is graded server-side
  (`app/api/progress/route.ts`), written to the ledger, and the learner model is
  a **projection** of that ledger — `verify` asserts that deleting the model and
  replaying the ledger reproduces it field-for-field.
- **One decision engine.** Home, Learn, the session result, the offline pack and
  `GET /api/next` all call `lib/decision.ts`; `verify` fails the build if a
  surface calls the engine directly.
- **Deterministic offline path.** The matcher and the rule-based Socratic tutor
  run with no network and no key; the AI layer is explicitly optional and the UI
  discloses which of offline/cloud answered.
- **Static/parity.** `verify:static` puts one learner history through both the
  server write path and the bundled static write path and requires the same
  model, the same next action and the same citations.
- **Accounts.** scrypt password hashing, per-account salt, signed HttpOnly
  session cookie, session-epoch revocation on logout, and a real right-to-erasure
  (`DELETE /api/profile`) and data export (`GET /api/my-data`).
- **Server-controlled teacher authorisation.** Class ownership is decided
  server-side (`lib/server/class-membership.ts`); a learner cannot promote
  themselves through an ordinary profile write.

## 3. Defects found and fixed in this pass

### 3.1 P0 — a concept served the SAME question over and over (FIXED)

**Symptom (user-reported):** "the same question quizzing me over and over."

**Root cause, measured.** `generateQuestionNear` deterministically picks the
draw *nearest the target band*. 44 of 135 base generators ignore the RNG and
emit one authored item, and `withDepth(base, deep, 0.5)` returns the base on half
the draws. The constant base therefore won the nearest-band pick on **every**
serve. Measured before the fix, on the app's own call shape: `what-is-code`
served **1 distinct item in 12**; `dictionaries` 1–8 in 30; aggregate over 135
concepts: 53 showed ≤8 distinct items.

**Fix.** `generateQuestionNear` gained a `served` list (oldest first). A
not-yet-served draw always wins; when the generator's whole catalogue is spent,
the fallback is the item served **longest ago**, so the sitting rotates instead
of pinning. `app/api/progress/route.ts` records each served key
(`${prompt}|${correctChoice}`) bounded to the last 12 and passes it through.

**Measured after the fix:** `distinct==1` concepts = **0** — no concept serves
the same item all sitting, and every concept with more than one item serves more
than one. Pinned by a new `verify` assertion.

**Honest limit:** the fix does not create content. After the deepening in §4.1,
20 concepts still expose ≤10 items (worst: 8), so those cycle within a long
sitting. See §4.1.

### 3.2 P1 — code and multi-line prompts rendered as one paragraph (FIXED)

33 of 135 generated prompts contain a newline (Python blocks, equations, bullet
lists). Every surface rendered them in a single proportional `<p>`, collapsing
indentation. New `lib/prompt.ts#splitPrompt` divides prose from code,
**losslessly** (segments read in order reconstruct the original character for
character — asserted on all 1080 draws, 0 mismatches), and a new
`components/prompt-text.tsx` renders code in `<pre class="qcode">`. Wired
through all five question surfaces and mirrored in the static kit. Detects code
in exactly 7 computing concepts; a maths question with two equations under a
prose heading is correctly left as prose.

### 3.3 P2 — dead weight removed

`components/exercise-sheet.tsx` (orphaned) and `scripts/i18n-exercise-book.mjs`
deleted; 11 dead i18n keys × 15 languages (165 lines) removed; the `verify`
i18n block updated to match. `npm run build:static` regenerated so `docs/` no
longer carries the deleted keys (verified: 0 occurrences).

## 4. Open defects, by priority

### 4.1 P1 — a tail of shallow concepts, and no non-MCQ responses

**Corrected by measurement.** The bank is **not** uniformly shallow. Measuring
every generator's distinct-item catalogue (400 draws each), AFTER the deepening
below: **72 of 135 concepts expose 51+ distinct items, 18 expose 21–50, 25
expose 11–20, and 20 expose 6–10. No concept exposes fewer than 8.** Total
distinct items: **14,813**, mean **~110 per concept**. So the repetition the
user saw was a *serving* bug (§3.1), not a content desert — and the fix means
the rich majority now rotate properly.

The real content gaps are narrower and different:

- **A shallow tail.** 20 concepts expose ≤10 items; the worst are now
  `rates-reaction`/`equilibria`/`photosynthesis`/`web-stack` (8) and
  `light-optics`/`magnetism`/`gravity-fields`/`astrophysics`/`periodic-table`/
  `digestion`/`biodiversity`/`algorithms-search` (9). These cannot sustain a
  long sitting and are the remaining content work. **Deepened this pass:** the
  three worst were raised — `loops` **4 → 55**, `functions-code` **7 → 38**,
  `digestion` **6 → 9** — by adding genuinely distinct angles (count-iterations,
  last-printed, product-accumulator and while-loop for `loops`; composition and
  returned-value for `functions-code`; enzyme/substrate both ways and bile's
  role for `digestion`), not seed jitter.
- **No non-MCQ responses at all.** `extended_response` is declared by the demand
  ladder and has **0** items anywhere (`content-check`: "unreachable for every
  concept"). This is the assessment gap (§4.3), not a bank-size problem.
- `content-check` still reports **55 practisable concepts with a content gap**
  at the *dimension* level — a concept may have many items but not yet reach
  `data_interpretation` or `multi_step`.

### 4.2 P1 — curricula are stage-windows, not distinct curriculum maps

25 specifications across ~25 countries each resolve to **48–135 concepts drawn
from the same 135-concept bank** (measured: `any-independent/advanced` = 135,
`pk-matric/class6-8` = 48, every other level = 94–131). Selecting a country and
a board changes the *stage window* and the labels, not the underlying set of
concepts or their objectives. Per §5 of the brief — "do not claim curriculum
support merely because a dropdown contains a country" — these courses are
**partially supported at best**: a curriculum map exists and a difficulty window
exists, but distinct per-board objectives, provenance, and reviewed content do
not. There is no 1EdTech CASE-shaped standards model in the tree.

### 4.3 P1 — assessment is MCQ-only

`Question` (`lib/types.ts:73`) is `{ prompt, choices[4], answer, explanation,
misconceptionTags }`; grading is `choiceIndex === q.answer`. The brief's §6 list
(numeric entry, algebraic entry, short answer, structured response, graphs,
tables, code, proof, multi-step, data analysis, extended explanation,
experimental reasoning) is **entirely unimplemented** except as MCQ. The only
free-entry numeric input in the tree is in `components/own-paper.tsx`, and it is
not part of the graded question loop. `extended_response` (§4.1) is the visible
tip of this.

### 4.4 P2 — `.topic` CSS exists in one kit only

`.topic` is defined in `app/globals.css` but **not** in `docs/app.css`, and the
static `viewCurriculum` renders `.items`/`.tag` markup instead. The two builds
do not render the same Learn screen. (Cleanup gap 5.)

### 4.5 P2 — `verify` still asserts some behaviour by page-source regex

Several Learn assertions in `scripts/verify-engines.mjs` regex the page's source
text, so they would pass with a wrong `className` or a broken row map. The
audit's own principle (§11 of the brief: assert behaviour, not prose) says these
should read computed output. Partially addressed this pass for the question
path; the Learn block remains.

### 4.6 P2 — stage count is hard-coded in the page, not owned by the genome

`app/learn/[subject]/page.tsx` hard-codes `[0,1,2,3,4,5]` and inline chip
margins; `STAGE_NAMES` exists (`lib/genome.ts:238`) but no `STAGE_IDS` array
does. (Cleanup gap 4.)

### 4.7 P2 — the route re-derives recall/proof instead of using its owner

`stateChips` in `app/learn/[subject]/page.tsx` recomputes recall/proof inline
rather than routing through `lib/evidence-view.ts#conceptKnowledge`. (Cleanup
gap 3.)

## 5. Security, privacy and child-safety

**Present:** scrypt + per-account salt; signed session cookie; `HttpOnly`;
`SameSite=Lax`; session-epoch revocation; server-side class authorisation;
right-to-erasure; learner data export.

**Gaps (P1/P2):**

- ~~**No `Secure` flag** on the session cookie.~~ **FIXED this pass.**
  `Secure` now follows the scheme: set over HTTPS (and behind a
  TLS-terminating proxy via `x-forwarded-proto`), omitted on the plain-HTTP
  local/school deployments this product supports. Pinned by a `verify`
  assertion that drives the real module.
- **No rate limiting** on `auth/login`, `auth/signup`, or the AI routes. A
  brute-force / abuse surface.
- **No CSRF token.** `SameSite=Lax` mitigates the common cases but is not a
  substitute for a token on state-changing POSTs.
- **No email verification** — disclosed honestly in the README ("OpenMind sends
  no mail"), but a child-facing service should not treat an unverified address
  as an identity.
- **No age gating / safeguarding escalation path** in code. The brief's §15 and
  §31 require input/output safety filtering, prompt-injection resistance, an AI
  disclosure, and an escalation route; the disclosure exists (three lines in 15
  languages), the rest does not.
- **No audit trail** for authentication or authorisation events.

## 6. Internationalisation, accessibility, interoperability

- **i18n:** 15 languages at key parity, automatic RTL for Arabic/Urdu/Farsi, 60+
  country picker, per-key fallback. **Honest limit:** non-English dictionaries
  are machine-drafted; the README says so and it is true. Content (lesson text,
  question text, misconceptions) is **not** localised, only the interface.
- **Accessibility:** `verify:render` checks icon-only accessible names, landmark
  naming, design-token definition and footer structure. WCAG 2.2 AA is **not**
  formally tested; keyboard-only, screen-reader, 200% zoom, reduced-motion and
  math/graph accessibility have no regression coverage.
- **Interoperability:** no CASE, LTI, OneRoster or QTI adapter exists. The brief
  asks for clean adapter *interfaces* even before implementations; there are
  none. This is P2 (design for it) rather than P1 (nothing claims it).

## 7. Testing gaps

- No unit-test framework; all coverage is script-driven. This is a deliberate
  and defensible choice, but it means **no browser-driven regression test runs
  in the default gate set** — `verify:ui` exists but needs a local Chrome and is
  not part of `verify`.
- The default gates prove engines and served bytes; they do not drive a real
  browser, a real service worker, or a real localStorage. `verify:static` says
  so explicitly.
- Recommendation **causality** (change one evidence event → decision changes) is
  asserted for the engine, but not yet as a per-surface sweep.
- No simulated-learner journey harness across 100+ journeys (brief §12).

## 10. What this audit does NOT establish

- It does **not** establish educational effectiveness. Software correctness and
  learning gains are different claims; the brief (§35) is explicit that only real
  learner research can support the second, and no such research exists yet.
- It does **not** establish parity with any named organisation. No comparative
  evidence was gathered and none is claimed.
- The gates prove engines and served bytes, not a human's experience. §51's
  fresh-user test has not been run.
